# IEC 61508 application notes

Scope: the 2010 editions and the 2016 technical specification identified in
[Sources](SOURCES.md). Clause summaries below are selective. Part 7 explains
techniques in informative annexes; its descriptions are not independent
evidence that a particular implementation achieves a safety integrity level.

## Lifecycle and responsibility

**Source reading.** IEC 61508-1 connects technical work to a safety lifecycle,
identified responsibilities, competence and controlled documentation. A set
of source files and passing tests is only part of that work.
([IEC1](SOURCES.md#iec1), clauses 1 and 6, PDF pp. 11, 16-18.)

**Application to escsafelib.** The shared assistant workflow helps retain
decisions, but Claude and Codex reviews do not establish the responsible
organization's competence, assessment independence or acceptance of safety
claims. The integrator still has to identify the safety function, operating
conditions and required integrity. No such project-specific allocation is
created by these notes.

## Specify behavior and assumptions before claiming suitability

**Source reading.** Software safety requirements derive from system needs
and address behavior, interfaces, capacity, timing, misuse and hardware
constraints. Configuration data and out-of-range or late interface values
also need consideration. ([IEC3](SOURCES.md#iec3), 7.2.2, PDF pp. 24-26.)

**Application to escsafelib.** A module contract should make its units,
permitted ranges, initialization, error response and execution assumptions
visible to its caller. Examples worth retaining in an integration record:

- `sarray` capacities count elements; `smemory` and `sstring` capacities
  count bytes. A declared capacity must describe real, live storage.
- Fixed-point and scaling routines have rounding and representable-range
  contracts. A numerical answer that is mathematically close may still
  violate the caller's required rounding behavior.
- `swatch` needs a caller-provided time base and polling; `sfault` counts
  update calls. Their configuration does not establish the system's allowed
  detection and reaction time by itself.
- Leaving an output unchanged on failure requires the caller to inspect
  status. A previously valid value is not automatically safe to reuse.
  Stateful APIs also have documented diagnostic state changes; inspect the
  individual function contract rather than applying a blanket no-write rule.

These are integration interpretations. The actual contracts remain in the
paired sources and [project guidance](../../CLAUDE.md).

## Reuse requires an argument and information for the integrator

**Source reading.** Part 3 distinguishes compliant development, proven use,
and assessment of software developed outside the compliant process. Reuse
needs a justified route and a safety manual with the relevant element
properties and assumptions. Annex D addresses identity, configuration,
use constraints, outstanding anomalies and supporting evidence.
([IEC3](SOURCES.md#iec3), 7.4.2.12-13, PDF pp. 29-31; Annex D,
PDF pp. 99-100.)

**Application to escsafelib.** Copying a header/source pair into another
project should carry an identifiable version and the usage constraints
needed by that project. Useful integration information includes compiler
and target settings, concurrency restrictions, known limitations, error
handling and the tests relevant to the chosen use. Doxygen and this index
are inputs to such a record; they are not a completed compliant-item safety
manual or an accepted reuse justification.

**Source reading.** IEC TS 61508-3-1:2016 is a specific proven-in-use route
for SIL 1 or SIL 2. It depends on documented prior operating combinations,
configuration and failure observation, and analysis of the intended use.
Its 4.9 does not carry proven-in-use status forward after a modification.
([IEC-TS31](SOURCES.md#iec-ts31), clauses 1 and 4, PDF pp. 8-11.)

**Evidence limit.** Commit age, downloads, host test counts and an absence
of reported bugs do not establish this operational history. The repository
review did not establish a proven-in-use claim. The specification's scope
must not be generalized into a claim about every possible reuse route.

## Verification and development tools

**Source reading.** Part 3 combines module review and testing, specifies
integration checks and recorded results, and requires verification of code,
data and timing. It also addresses the selection, failure mechanisms,
validation and version/configuration control of development tools.
([IEC3](SOURCES.md#iec3), 7.4.4, PDF pp. 32-35; 7.4.6-8 and 7.5,
PDF pp. 36-38; 7.9, PDF pp. 43, 46.)

**Application to escsafelib.** Compilers, the Python generators, static
analyzers, coverage tooling and custom checkers all contribute to the
argument. The negative controls in the existing tools demonstrate selected
failure-detection paths. They do not qualify the whole tool or all its
versions. Reproducible generation demonstrates consistency with a generator;
it does not independently demonstrate that the generator implements the
right requirement. See the [evidence map](EVIDENCE_MAP.md).

Part 7's interface, boundary and error-seeding discussions fit the project's
boundary tests and mutants. However, killing a curated set of mutants is
not a statistical software failure-rate estimate. Part 7 itself identifies
limitations of inference from seeded errors.
([IEC7](SOURCES.md#iec7), C.5.2-C.5.6, PDF pp. 92-94.)

## Diagnostics are evaluated in the actual system

**Source reading.** Part 2's diagnostic tables describe techniques and
potential coverage subject to the analysis in Annex C. Diagnostic coverage
depends on the dangerous hardware failure modes detected, with their failure
rates; it is not source-code coverage.
([IEC2](SOURCES.md#iec2), Annex A introduction, Table A.6 and Annex C.1,
PDF pp. 50, 56, 74.)

**Application to escsafelib.** Do not assign a coverage percentage to
`sdiagRamTestDestructive` solely because its comment names a March test.
The algorithm variant, memory organization, access width, tested region,
execution conditions and fault model matter. The generic checkerboard/March
entry in Table A.6 is not a blanket endorsement of every March variant.
The Windows aliasing harness exercises an address-aliasing scenario; it does
not demonstrate all stuck-at, coupling or transient faults. Part 7 also
distinguishes persistent memory tests from measures addressing soft errors.
([IEC7](SOURCES.md#iec7), A.5 and A.5.1, PDF pp. 19-20.)

Likewise, `swatch` is software time supervision, not an independent hardware
watchdog. A stalled execution context or shared failed clock can disable
both the monitored task and its monitor. Part 7 distinguishes a separate
watchdog time base, logical sequence monitoring and their combination.
([IEC2](SOURCES.md#iec2), Table A.10, PDF p. 58;
[IEC7](SOURCES.md#iec7), A.9.1-A.9.5, PDF p. 25.)

These limits support the existing library boundary: hardware-specific tests,
fault reaction and target validation belong to the integrating system.
They are not a reason to add a HAL or a target dependency to this library.
