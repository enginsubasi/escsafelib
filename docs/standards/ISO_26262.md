# ISO 26262 application notes

Scope: the local BS ISO 26262:2018 parts 6, 8, 9 and 10 in
[Sources](SOURCES.md). These notes concern possible automotive reuse.
They do not assign an ASIL to the library or select the integrator's
compliance route. Part 10 provides explanatory guidance; keep its examples
distinct from the requirements in the other parts.

## Requirements and design

**Source reading.** Part 6 addresses language restrictions and coding
guidelines, software safety requirements derived from the system, hardware
interfaces, and verifiable unit design. Its tables contain different
recommendation strengths by ASIL; this note does not replace their selection
and justification rules. ([ISO6](SOURCES.md#iso6), 5.4, 6.4 and 8.4,
PDF pp. 16-19, 27-29.)

**Application to escsafelib.** Bounded interfaces, fixed-width types,
caller-owned memory, simple control flow and explicit status codes are useful
design choices. Their presence does not prove that a vehicle safety
requirement is satisfied. The caller must supply a meaningful operating
range, safe reaction, scheduling model and hardware assumptions.

Part 8 requires traceability from requirements to their sources, design or
derived requirements, and verification specification.
([ISO8](SOURCES.md#iso8), 6.4.3, PDF pp. 25-26.)

For this repository, a function name and a test count do not provide that
traceability by themselves. An integration argument should be able to link
a stated contract to the relevant tests and the results for a specific
revision. This review found useful contracts and tests, but did not establish
a complete requirements-to-verification matrix.

## Distinguish the different verification questions

**Source reading.** Unit verification combines techniques such as review,
analysis, requirements-based tests, interface tests and fault injection.
Requirements coverage and structural coverage are separate checks. When
structural coverage is insufficient, additional tests or a supported
rationale are needed. ([ISO6](SOURCES.md#iso6), 9.4.2-4 and Tables 7-9,
PDF pp. 31-33.)

**Application to escsafelib.** The current suites, mutants and analyzers
provide complementary evidence. [coverage.sh](../../tools/coverage.sh)
collects gcov line and branch measurements, including integration-suite
contributions where applicable. Since 2026-11-07 it also reports gcc's
condition coverage (`-fcondition-coverage`, gcc 14 and later), which is an
MC/DC measurement of the module against its own suite. Part 6 Table 9 gives
MC/DC its strongest recommendation for ASIL D. On 2026-11-07 every
measured gap in all fourteen modules was classified as a missing case or an
unreachable condition; the missing cases were added and the remaining
conditions are listed with their reasons in `CLAUDE.md`. That is a
host-side unit measurement with gcc's masking form of MC/DC, made by the
repository's own tooling; it is not a tool-qualified measurement, not a
target measurement, and not evidence that the table's expectation is met
for any item. Branch coverage must still not be presented
as the same measurement. A percentage
also does not show that every required error response was asserted.

Part 6 treats verification at the software architecture level separately,
including function/call coverage and production configuration.
([ISO6](SOURCES.md#iso6), 10.4.4-7 and Table 12, PDF p. 37.)

The sample [integration suite](../../test/Integration_Test/Integration_Test.c)
helps demonstrate interactions among selected modules. It is not the
integration test of a customer's complete ECU software or every library API
combination. Document which interfaces and behaviors an actual use exercises.

## Host results and the target environment

**Source reading.** Where unit or integration tests use a different
environment, the differences are analyzed to determine additional target
tests. Testing the embedded software addresses fulfillment of the software
requirements in the target environment.
([ISO6](SOURCES.md#iso6), 9.4.5, 10.4.7 and clause 11,
PDF pp. 33, 37-40.)

**Application to escsafelib.** A successful ARM compilation establishes
buildability. Host runs do not establish ARM execution, memory ordering,
interrupt behavior, alignment behavior, worst-case execution time or stack
use on the selected target. The project's explicit host/target boundary
should accompany any transferred test evidence. No target testing was
performed for these notes.

## Existing component qualification and SEooC are different routes

**Source reading.** Part 8 clause 12 addresses qualification of existing
software components. It calls for identification, requirements, intended-use
and configuration information, suitable development-process evidence,
qualification planning, verification and documented results. Its verification
evidence is valid for an unchanged implementation, and its suitability for
the intended use must be checked.
([ISO8](SOURCES.md#iso8), 12.1-12.5, PDF pp. 44-47.)

Part 10 explains an SEooC as an element developed under the ISO 26262 process
using explicit assumptions about requirements and context. Those assumptions
are then checked in the actual item. It distinguishes this from qualification
of an existing component not necessarily developed under that process.
([ISO10](SOURCES.md#iso10), 9.1 and 9.2.4, PDF pp. 59-60, 65-67.)

**Application to escsafelib.** Being generic or reusable does not make this
library a developed SEooC, and adding these notes does not retroactively
qualify it. Useful inputs to a future reuse argument are exact source
identity, numerical behavior, error semantics, memory ownership, timing,
tool settings, known anomalies and evidence mapped to the actual use.
After a copied module is changed, the old evidence must be reassessed.

## Tool confidence depends on the tool's use

**Source reading.** Part 8 considers whether a tool can introduce or miss a
safety-related error and whether its erroneous output will be prevented or
detected. Tool configuration, use cases, environment, known issues and
interdependencies matter. A tool confidence level is not simply a property
of a vendor or executable name.
([ISO8](SOURCES.md#iso8), 11.4.2-11.4.6, PDF pp. 39-41.)

**Application to escsafelib.** Evaluate the compilers, source/test generators,
cppcheck addon, coverage tools and custom checkers in their actual roles.
Two generators with the same erroneous assumption can make implementation
and expected results agree. A control proving that an analyzer catches one
defect does not prove complete analysis coverage. The same reasoning applies
to AI-authored code and reviews: retain verifiable outputs and independent
checks, without automatically assigning a TCL or claiming qualification.

## Independence, changes and evidence retention

**Source reading.** Part 9 requires analysis of plausible dependent failures,
including shared resources, information and development faults, and measures
addressing their causes or effects.
([ISO9](SOURCES.md#iso9), 7.4, PDF pp. 22-24.)

**Application to escsafelib.** Two values supplied to `svote` are not proven
independent channels. They may share a sensor, reference, clock, calibration,
memory or software defect. Similarly, a monitor running in the same stalled
context as its subject cannot demonstrate freedom from interference.
Module source independence is useful packaging, not a system independence
argument or automatic justification for ASIL decomposition.

Part 8 addresses reproducible configuration and the impact of changes on
interfaces, work products and subsequent verification.
([ISO8](SOURCES.md#iso8), 7.4 and 8.4.2-4, PDF pp. 27, 29.)
For this project, relevant evidence identifies the commit, generated inputs,
compiler and flags, target assumptions, test commands/results and accepted
limitations. Git and CI help retain this information; the existence of either
does not establish all of the required lifecycle work products.
